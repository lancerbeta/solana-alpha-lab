# TASK-34A Documentation Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a deterministic, repository-native operator navigation layer that detects stale Project Sources mirrors without treating them as canonical truth.

**Architecture:** `task34a_documentation_foundation.py` resolves the activated Project Sources release and performs an optional read-only mirror comparison. A small CLI renders the dynamic card; the existing Catalog generator emits a static navigation reference and the existing CI gate verifies it. Runbooks link only to these deterministic entrypoints and stop at external-authority boundaries.

**Tech Stack:** Python 3.13, PyYAML, JSON Schema Draft 2020-12, Python `unittest`, existing Catalog generator and locked `uv` validation.

## Global Constraints

- `docs/project_sources/release_registry_v1.yaml` plus its hash-bound owner-smoke receipt is the activation authority; an application-managed local Sources directory is never canonical.
- The optional `--sources-dir` input is read-only and must never be committed, persisted, or echoed as an absolute path.
- Mirror states are exactly `MIRROR_MATCHES_ACTIVE_RELEASE`, `STALE_MIRROR_ACTIVE_RELEASE_CONFIRMED`, `MIRROR_UNAVAILABLE`, and `MIRROR_CONFLICT_REQUIRES_CONTROL_REVIEW`.
- Missing or stale mirror bytes may not demote a proven activated release; a registry/receipt contradiction fails closed and blocks task selection.
- No provider/API/RPC/WSS call, credential access, raw-data write, dependency change, wallet/signer/transaction action, cash action, or Project Sources UI mutation.
- Use existing `scripts/generate_navigation.py`, `scripts/validate_catalog.py`, and `scripts/validate_ci.py`; do not add a CI workflow or package.
- Generated Catalog files are regenerated, never manually edited.
